Thermal Framework: Stress Definition and Cross-Team Execution

Status: Proposed for alignment. Scope: Current and future products, including thermally constrained platforms.

Ownership: Thermal owns the framework; contributing teams supply requirements and technical evidence; PIE verifies. Named DRIs, dates, and technical approvals remain pending.

Delivery status: This is a local review page prepared for Confluence publication, not a published Confluence page or an approved test specification. No hardware tests or platform integrations have been performed. Publication requires a destination space, parent page, and authorized publishing access.

1. Summary and expected outcomes

Establish what to test, why the workload is appropriate, and what constitutes acceptable behavior.

  1. A reusable guideline for deriving stress levels for future projects, by product category where evidence supports reuse.
  2. A common SW toolset and testing approach with minimal changes to existing tools and configurable project profiles.
  3. Project profiles linking workloads, platform limits, thermal controls, performance, and recovery, with validation evidence before approval.

Supported usage → usage evidence + platform constraints → stress definition → common execution → verification and approval.

Category grouping enables reuse; it must not conceal meaningful platform differences. Candidate categories include music playback, HDMI/home theater, and applicable video/display roles. Product must confirm membership. The source term “Male transducer” requires clarification before use as a category.

2. Stress-definition principles and reusable guideline

2.1 Agree on definitions before selecting numbers

Proposed stress levels; definitions require stakeholder approval
LevelDefinitionRequired basis
Baseline: typical active useTime-weighted P50 of a defined demand metric during active playback; approximately half of playback time is above this level.Agreed population, metric, sampling window, and weighting. Distinguish from an engineering reference baseline.
Outlier: high-demand active useTime-weighted P99 of the same metric and population; approximately 1% of playback time is above this level.Valid usage data, duration/concurrency analysis, and sufficient coverage. P99 is proposed, not yet approved.
Worst supported operationPhysically credible supported workloads and environmental combinations at stated operating boundaries.Product requirements, hardware limits, and thermal characterization.
Abnormal/protection conditionCredible conditions outside supported operation, including defined abusive conditions requiring protection assessment.Approved safety boundaries, protective behavior, and recovery requirements; normal functionality is not necessarily required.
  • Define “higher demand”: CPU utilization and allocated memory alone do not establish thermal severity.
  • Specify active-playback eligibility, population, timestamp coverage, units, aggregation window, and weighting. A fleet-time distribution is not necessarily a typical-device distribution.
  • For a selected weighted empirical quantile convention, accumulate valid observed duration by metric value and locate the first value reaching the chosen fraction of total duration. Document interpolation, ties, and data gaps; do not count unobserved gaps as valid exposure.
  • Review confidence, sampling bias, and throttling that may hide requested demand. Do not claim exact exceedance fractions for discrete values or ties.
  • Select realistic joint scenarios with appropriate duration; do not combine independent per-variable P99 values into an unsupported scenario. P99 workload does not imply P99 temperature.
  • Supplement playback statistics with applicable standby, update, charging, and interface scenarios.
  • Keep supported-operation criteria separate from protection-test criteria. Field statistics do not replace hardware limits.

StepActivityOutput / review criterion
1. ClassifyIdentify supported functions, category, SoC/DDR/build, and thermal constraints.Product-approved scenario profile; category membership justified.
2. Establish evidenceUse telemetry and application profiling; use justified predecessor/category evidence provisionally when necessary.Usage model with coverage, uncertainty, assumptions, and reassessment trigger.

Reuse a category profile only when supported usage and measured platform behavior justify it. Do not scale parameters solely by DDR capacity or assume identical commands create equivalent stress. New-project assumptions remain provisional until validated.

Use the project profile template for one scenario per profile. Copy it for each applicable level. Nulls and empty lists mean unresolved/not supplied, never zero, not applicable, or passed. It is a documentation template, not a runnable configuration or validation schema.

3. Common SW approach — reuse first, minimal changes

Existing tools + shared execution/reporting conventions + configurable profiles + thin platform integrations where needed.

Repository inventory: At preparation, the tools directory contains only its README; no thermal runner, vendor integration, telemetry dataset, or existing build/test configuration was found. Consequently this package defines the interface and handoff, rather than inventing a runner or claiming hardware support. SW must identify the actual tool locations and owners before code changes are scoped.

3.1 Minimal-change implementation handoff

  1. Inventory available tools, source locations, versions, owners, platform coverage, and known limitations.
  2. Map existing capabilities to the common contract; prefer configuration changes over forks or new infrastructure.
  3. Propose only the missing integrations or reporting extensions, with owners and existing validation commands.
  4. Pilot representative platforms, including a constrained product; demonstrate repeatability and expose unsupported capabilities.

3.2 Constrained products and acceptance

Requested demand → achieved demand → limiting mechanism → functional impact → coverage disposition.

  • Expected throttling is assessed against the approved product requirement; it is neither automatically a pass nor a failure.
  • Allocation failure, OOM, unexpected workload exit, or missing required telemetry blocks an affirmative result. Optional unavailable metrics require an explicit coverage assessment.
  • Record execution validity separately from product acceptance. Invalid execution cannot yield a pass; unresolved coverage remains pending.
  • Evaluate software optimization, power-management profiles, approved performance/feature restrictions, or hardware changes as design alternatives.
  • Approve workload substitutions or complementary tests only with evidence of retained and lost coverage. Do not lower requirements merely to pass.
  • Keep protection enabled. Special characterization requires approved monitoring, boundaries, and stop conditions.

SW acceptance: Common execution and reporting are demonstrated on representative projects, including a constrained platform, without concealing achieved-load differences or capability gaps.

6. Completion and maintenance

  • A new project can derive justified settings without undocumented historical assumptions.
  • Current profiles have measured evidence or explicit provisional status.
  • Common tools demonstrate repeatability with minimal necessary changes.
  • Constrained-product performance and coverage limitations remain visible.
  • Protection, recovery, and exceptions have approved criteria and evidence.
  • GDM teams can reproduce and interpret results; technical approvals are recorded.

Reassess affected profiles when usage, features, SoC/DDR, software demand, thermal policies, sensors, or mechanical configuration changes. Record the impact assessment and required revalidation.

Scenario → justified workload → achieved stress → thermal and functional behavior → acceptance evidence.
