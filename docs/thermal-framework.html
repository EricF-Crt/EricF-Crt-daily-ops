1. Executive Summary

Establish a consistent, evidence-based framework for defining thermal stress, executing tests, and evaluating product behavior. The goal is not merely to update current project numbers.

  1. Reusable guideline: Derive future-project stress levels by category where evidence supports reuse—not just select today's numbers.
  2. Common SW approach: Reuse existing tools with minimal changes, configurable profiles, and consistent evidence.
  3. Verified project profiles: Connect workload, limits, protection, performance, and recovery before approval.

Product usage → resource demand + platform limits → stress definition → common execution → verification and approval.

Shared settings are acceptable when evidence supports their coverage. Different memory capacities alone neither justify nor invalidate a shared recipe.

2. Core Principles

Start with supported functions, then account for SoC/DDR, software, and thermal constraints. Candidate categories include music playback, HDMI/home theater, and applicable video/display roles. Product must confirm membership; category reuse must not conceal platform differences.

P50/P99 are proposed principles requiring agreement—not approved project settings.

Rules for deriving accurate parameters

  • Classify by supported functions; account separately for SoC, DDR, software, and thermal constraints.
  • Use DS/SW evidence for real usage; Thermal translates that evidence into thermal requirements.
  • Define the demand metric and population before calculating percentiles. CPU utilization and memory allocation alone do not establish thermal severity.
  • Preserve realistic concurrency and duration; do not combine unrelated P99 values.
  • Account for missing data, throttling, uncertainty, and ties in the distribution.
  • Include applicable non-playback scenarios.
  • Keep supported-operation requirements separate from abnormal-condition protection.

DS/SW provide usage evidence and reproducible workloads; Product confirms supported use; Thermal sets thermal coverage and acceptance. Detailed statistical requirements are in the methodology notes.

Future-project derivation method

Classify → establish evidence → derive workloads → characterize → approve.

Reuse a category profile only when supported usage and measured platform behavior justify it. Do not scale parameters solely by DDR capacity or assume identical commands create equivalent stress. New-project assumptions remain provisional until validated.

Output: One versioned profile per scenario, with derivation rationale, evidence, criteria, and approvals. The profile template is a documentation aid, not executable configuration; empty fields are unresolved, never approval.

3. Common SW Approach

Existing tools + shared execution/reporting conventions + configurable profiles + thin platform integrations where needed.

Standardize execution and evidence, not platform thresholds or identical workloads. Identify existing tool owners and source locations before proposing code changes.

LayerCommon contractPlatform/project variation
ExecutionControlled invocation, timestamps, duration, and validity checks.Tools, threads, affinity, memory settings, and concurrency.
ObservationSynchronized evidence, explicit units, missing-data status.Sensor mappings and available Amlogic/Synaptics/MTK telemetry.
EvaluationExecution validity assessed before product acceptance.Limits, permitted degradation, protection, and recovery expectations.
ReportingRequested versus achieved demand, configuration, evidence, and disposition.Constraints, unsupported capabilities, and approved alternatives.

SW delivery sequence

Inventory → assess gaps → configure or minimally extend → pilot. Deliver a capability matrix, a scoped change proposal, and repeatability evidence. Prefer configuration over forks; use existing validation commands for changes.

Thermally constrained products

Requested demand → achieved demand → limiting mechanism → functional impact → coverage disposition.

  • Expected throttling is assessed against the approved product requirement; it is neither automatically a pass nor a failure.
  • Separate execution validity from acceptance: allocation failure, OOM, unexpected exit, or missing required telemetry cannot yield a pass. Optional missing metrics require a coverage assessment.
  • Evaluate software optimization, power-management profiles, approved performance/feature restrictions, or hardware changes as design alternatives.
  • Approve workload substitutions or complementary tests only with evidence of retained and lost coverage. Do not lower requirements merely to pass.
  • Keep protection enabled. Special characterization requires approved monitoring, boundaries, and stop conditions.

SW acceptance: Common execution and reporting are demonstrated on representative projects, including a constrained platform, without concealing achieved-load differences or capability gaps.

7. Completion Criteria

  • A new project can derive justified settings without undocumented historical assumptions.
  • Current profiles have measured evidence or explicit provisional status.
  • Common tools demonstrate repeatability with minimal necessary changes.
  • Constrained-product performance and coverage limitations remain visible.
  • Protection, recovery, and exceptions have approved criteria and evidence.
  • GDM teams can reproduce and interpret results; technical approvals are recorded.

Track: Action/decision · DRI · Dependency · Deliverable · Acceptance criterion · Date · Evidence · Status.

Reassess affected profiles when usage, features, SoC/DDR, software demand, thermal policies, sensors, or mechanical configuration changes. Record the impact assessment and required revalidation.

Scenario → justified workload → achieved stress → thermal and functional behavior → acceptance evidence.

Supporting material and publication

Working artifacts

  • Project profile template: one scenario per profile. Nulls/empty lists mean unresolved, not zero, N/A, or passed. This is not a runnable configuration or validation schema.
  • Action register: action/decision, DRI, dependency, deliverable, acceptance criterion, date, evidence, and status.

Methodology notes for DS/SW review

  • Specify active-playback eligibility, population, timestamp coverage, metric units, aggregation window, and weighting. Fleet playback time and typical-device usage are different populations.
  • For an agreed weighted empirical quantile convention, accumulate valid observed duration by metric value and locate the first value reaching the selected fraction of total duration. Record the convention and treatment of ties/interpolation; exclude unobserved gaps.
  • Assess confidence, sampling bias, and throttling that can mask demand. Ties/discrete values can change exact exceedance fractions.
  • Preserve realistic concurrency and peak duration; do not combine unrelated P99 values. P99 workload does not imply P99 temperature.
